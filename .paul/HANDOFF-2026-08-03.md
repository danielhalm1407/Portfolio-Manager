## What Was Done

This session was **diagnosis and discussion only — no code was written.** The one file
modification was made by the user by hand.

### The bug that reopened the phase

Cell 15 of `orders/rebalance_live_debug.py` returned zero fills while the TWS Trade Log showed five
executions from the same day (2026-08-03, 08:00–14:30). The standing explanation — the "midnight
ceiling" documented on 2026-08-02 — could not account for it, because those fills were *today's*
and therefore inside the window TWS serves.

**Root cause: `ExecutionFilter.clientId`.** The orders had been placed by
`pipelines/rebalance_live.py`, which uses client id **151**. Cell 15 was asking as **161**, the
debug harness's own id. Changing the filter to 151 returned all five fills.

**Critical refinement, easy to get wrong on resume:** the *connection* was still `CLIENT_ID = 161`
when this worked. Only the filter value changed. So the connection was never the restriction and
**the Master API client ID is not required** on this setup. An early theory that connection-level
scoping was to blame is wrong and should not be carried forward. The prior note that `client_id=0`
"returned nothing" was recorded on a Sunday with no fills at all, so it tested nothing.

### The second defect the fix exposed

Once fills came back, the `ts` column proved not to agree with the TWS Trade Log, and not by a
constant offset:

| Symbol | Venue | TWS Trade Log | `ts` | Delta |
|--------|-------|---------------|------|-------|
| BARC | LSE | 08:00:10 | 09:00:10 | +1h |
| AINF | LSEETF | 08:00:12 | 09:00:12 | +1h |
| HSBA | LSE | 08:00:19 | 09:00:19 | +1h |
| 5MVL | IBIS2 | 08:04:45 | 09:04:45 | +1h |
| LNG | NYSE | 14:30:25 | 09:30:25 | −5h |

Four rows shift one way, one the other — no single timezone pair explains that. `ts` has no
verified meaning, and the sort at `src/portutils/ingestion/ibkr_requests.py:2462` is ordering
stamps that are not on a common clock. LNG landing last is luck.

Suspected mechanism: `ibkr_requests.py:2460` does `df['time'].str.split(' ').str[:2]`, discarding
element `[2]` — which is where a timezone token would ride. The parse then *succeeds* on the
truncated remainder, so nothing ever errors. **Unverified — this is the first thing to prove.**

### The transparency finding

Investigating "why can't I just see the payload?" produced the structural answer:

- Callbacks print nothing on their own. `error()` reaches the terminal only because
  `ibkr_requests.py:780` is written to print it — which is why errors 2174 and 10314 were catchable
  and nothing else has been. `execDetails` prints nothing.
- The payload is destroyed at the callback boundary. `ibkr_requests.py:1159-1180` hand-picks 13
  fields off the `Execution` object into a dict; the object is garbage immediately after. Dropped
  fields include `clientId`, `acctNumber`, `exchange`, `lastLiquidity`, `orderRef`, and any
  timezone token on `time`.
- Therefore no logging level or downstream flag can recover it. It must be captured *at the
  callback*. `repr(execution)` dumps every field `ibapi` holds in one line.
