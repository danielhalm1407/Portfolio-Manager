<findings>
Cell 15 of [rebalance_live_debug.py](../../../orders/rebalance_live_debug.py#L564-L573) prints
`0 fills in the last 7 days` while the TWS Trade Log, set to "Last 7 Days", visibly shows fills
from JUL 27–31. A read-only probe fired the same request six ways against the live session.

1. **The 0 fills is not caused by anything in this function.** An empty `ExecutionFilter()` — no
   time, no clientId, no account — returned **0 fills with `execDetailsEnd` received**. A healthy
   TWS, asked for everything with no filter at all, answered "nothing". Every filtered variant
   matched it. There is no filter setting that turns this into rows.

2. **The clientId theory is dead.** Narrowing to `clientId=161` (the id the harness places orders
   under) also returned 0. The filter's clientId is not what is excluding the fills.

3. **This is the midnight ceiling, observed rather than quoted.** IB serves executions since
   midnight today; the latest fill in the Trade Log is JUL 31 and the probe ran on AUG 2. The Trade
   Log's *"Show trades for: Last 7 Days"* setting, though set and displayed, did not extend the API
   window in this session.

4. **TWS itself settled the time format, and both written sources were incomplete.** Error 10314,
   drawn by a deliberately malformed probe variant, states the spec: *"The correct format is
   yyyymmdd hh:mm:ss xx/xxxx ... E.g.: 20031126 15:59:00 US/Eastern ... You can also provide
   yyyymmddd-hh:mm:ss time is in UTC. Note that there is a dash between the date and time in UTC
   notation."* So a SPACE takes an explicit timezone suffix; a DASH means UTC and must carry none.
   The form this code sent — space, no timezone — is a deprecated third case, and TWS flags it with
   error 2174: *"...without explicit time zone ... Implied time zone functionality will be removed
   in the next API release."* Using UTC dash notation removes the warning and needs no
   timezone-database name.

5. **The 7-day workaround appears in ONE doc set only, and it is the legacy one.** The two IB
   doc sets disagree outright:

   | Source | Says |
   |---|---|
   | [github.io, TWS API **v9.72+** (legacy)](https://interactivebrokers.github.io/tws-api/executions_commissions.html) | *"If you want to request executions up to last 7 days, TWS's Trade Log setting 'Show trades for ...' must be adjusted to your requirement. Please note, that IB Gateway would be unable to change the Trade Log's settings..."* |
   | [Current docs site](https://www.interactivebrokers.com/docs/tws-api/doc/order-management/execution-details/request-execution-details) | *"Requests current day's (since midnight) executions ... **Only the current day's executions can be retrieved.**"* No workaround mentioned at all. |

   The archived twsapi discussion adds a detail the GUI in use may not match: *"connected to TWS
   with the **trade log** open with **all days checked**"*. That describes `Account → Trade Log`,
   which is a different window from the **Trades** panel (Trades/Summary tabs, `Show trades for:`
   dropdown) where the setting was actually changed. So the workaround was possibly never applied
   as documented — but it is equally possible it no longer exists, given the current doc set
   states a flat current-day limit.

   **Working assumption: roughly 24 hours / the current day is all this API path will give.**
   Genuine execution history has to come from IBKR's **Flex Web Service** (query + token created
   in Account Management), not from `reqExecutions`. That is a real constraint on the accounting
   engine, not merely an inconvenience in this one cell.

6. **Today cannot settle it, and that is worth stating rather than papering over.** The probe ran
   on **Sunday 02 Aug** — `market_hours_note()` confirmed the weekend — with the latest fills
   dated JUL 31. A working 7-day extension and a dead one produce the identical result of 0 today.
   The decisive test is the next trading day: once anything fills, cell 15 should show it within
   the same session. If it does, this function is sound and only *history* is limited.

**Conclusion: no behavioural defect explains the empty result.** The deliverables are a
non-deprecated time format, an accurate docstring, regression tests, and a terminal runner that
makes the IB callback traffic visible while diagnosing this class of problem.
</findings>
