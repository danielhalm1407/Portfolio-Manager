<objective>
## Goal
Turn 13-01's engine into an answer to the question the phase exists for: **how far out of the money
should the put be struck, and at what drawdown should it be monetised?** Run the Cartesian product
of those two parameters over the full history once, score every combination on a set of indicative
windows, and fit a smooth response surface so the optimum can be read between grid points as well as
on them.

## Purpose
The target variable here does not exist in any dataset. "Performance of a put struck at 0.92 of spot,
monetised at a 12% drawdown" is manufactured by running the simulator. That makes this a
**response-surface / surrogate-modelling** exercise: choose design points, run the simulator at each,
fit a cheap smooth approximation through the results, optimise over the approximation. The full
treatment is in the Obsidian vault at
`../obsidian_notes/Knowledge/Finance/Quant finance/Out-of-sample validation of strategy parameters.md`;
the decisions are in this phase's `CONTEXT.md`.

**Everything this plan reports is IN-SAMPLE by construction.** Every threshold is chosen looking at
the same windows it is scored on. That is not a defect to apologise for — it is the deliberate first
stage, and 13-03's CPCV is where it gets tested. Nothing here may be described as a validated result.

## The runtime constant this plan sizes from comes from 13-01.1, not 13-01
13-01's implementation context section 5 measured the simulator as **quadratic in bars** — 5.99
ms/bar at 250 bars, 28.63 ms/bar at 2,000 — extrapolating to ~6.5 min per configuration and ~11
hours for a two-axis grid. The cause is column growth in the output frame, not the rules and not the
fill model: `Book` retains every leg it has ever held, `Book.snapshot` iterates all of them, and
`Ledger.record_book` flattens all of them into an ever-widening row.

**That is fixed in 13-01.1**, an interruption plan between 13-01 and 13-02, by a constant-width
`StateLedger` subclass handed to the simulator through the `ledger=` argument it already accepts.
The full mechanism, the measurement and the reason it needed no boundary amendment are in
`13-01.1-PLAN.md`; they are not restated here.

**What this plan consumes from it, and the two obligations that come with it:**

1. **The single-run constant.** 13-01.1's SUMMARY records the measured ms/bar and the projected
   full-history single-run time. AC-1's projection multiplies THAT number. 13-01's original 6.5 min
   figure is stale by roughly 25x and must not be used — 13-01's AC-6 records the post-fix number
   for exactly this reason.

   **Corroborated independently while closing 13-01 (2026-09-26)**, on the actual
   `monetise_drawdown` structure this plan sweeps, not a synthetic 5.99→28.63 ms/bar
   extrapolation: `protective_put` (the same rule, floor and policy) measured **1.0–1.8s per
   full-history run** across several repeated runs (`research/validation/option_ladder_probe.py`
   cells 10/12; `outputs/option_monetisation/runtime_log.csv`), and the batch's own
   `monetise_drawdown` row measured **0.45s for the first configuration in a 5-config run**
   (`option_monetisation_batch.py`, after fixing a missing `ledger=NarrowLedger()` — see
   13-01-SUMMARY.md). Both are consistent with 13-01.1's number and safe to size a first grid
   from. **Not the same number as `put_spread`'s 1.78s or `collar`'s 2.34s** measured the same
   session — those two structures are NOT part of this plan (13-02 is long-put-only) and their
   runtimes do not apply here.

   **Part of why it is this fast: the 2026-09-21 reopen-reset fix (13-01 finding 1).** Before it,
   the monetise/reopen gate thrashed — 281 monetisations against 48 rolls over the full history,
   because the drawdown reference never reset and kept re-triggering. After resetting it on
   REOPEN (never on a roll), the same full-history run fires far fewer times (13-01's SUMMARY has
   the exact before/after counts). Fewer monetise/reopen cycles is fewer per-bar option legs
   churned, which is part of the measured speed above, not just the narrow ledger's column-count
   fix alone — worth knowing before assuming the grid's cost scales linearly with bars regardless
   of how often a cell's own parameters cause it to trigger.
2. **The narrow ledger cannot explain its own equity path.** Per-leg columns like
   `"SPY 2009-03-20 P450_position"` no longer exist. Every configuration must therefore persist the
   BLOTTER and the rule's per-bar history alongside its equity series, and option lifecycle events
   are derived from the blotter through 13-01.1's `classify_option_events` — the single shared
   definition, so this plan's path panels and 13-01's Task 3 cannot disagree about what a roll is.
   AC-2 requires all three artefacts.

## AC-1: The grid is an explicit Cartesian product, and its size is recorded
```gherkin
Given a moneyness axis and a monetisation-drawdown axis stated as explicit lists
When the sweep is constructed
Then it is the full Cartesian product of the two, with every combination run exactly once
And the total number of combinations is printed and written to the output directory as the
     TRIAL COUNT, because that is the number a probability-of-backtest-overfitting figure needs
And the projected runtime is printed BEFORE the sweep starts, so an unaffordable grid is
     caught at the top rather than after an hour
And that projection is combinations x the single-run constant MEASURED AND RECORDED IN
     13-01.1's SUMMARY, NOT 13-01's original 6.5 min figure, which 13-01.1 invalidates by
     roughly 25x — 13-01 section 9's process note says the measurement must lead, and citing a
     recorded number rather than a remembered one is what makes that structural

     are written to the output directory, so the next plan sizing a third axis has a real
     constant to size from
```

## AC-2: Each combination is simulated once over the full history, and scored by slicing
```gherkin
Given a parameter combination
When the sweep runs it
Then the simulator is invoked ONCE over the full 2006-01-09 to 2026-09-18 window
And THREE artefacts are persisted, keyed by the combination, because under the narrow ledger
     the equity series alone can no longer explain itself: the per-bar equity frame, the
```
