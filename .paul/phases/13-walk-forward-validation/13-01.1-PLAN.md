## Why this plan exists, and why it is a decimal
13-01 stopped mid-APPLY. Tasks 1 and 2 are complete and verified; Task 3's code exists but its
full-history run was deliberately not completed, and 13-01's checkpoint was never reached. The
reason is recorded in `13-01-IMPLEMENTATION-CONTEXT.md` section 5: **the simulator is quadratic in
bars**, so 13-01's own AC-5 run is ~45 minutes and 13-02's grid would be ~11 hours.

That is an interruption to planned work, not a new milestone, so it takes a decimal plan number
(PAUL rule 12). It sits between 13-01 and 13-02 because **both** depend on it: 13-01's AC-6 requires
a measured single-run wall-clock that 13-02 sizes its grid from, and a number measured before this
fix would be stale by roughly 25x the moment it was recorded.

## Goal
Two things, and nothing else:
1. Make ONE simulator run linear in bars, without editing anything on 13-01's DO NOT CHANGE list.
2. Build the probe that lets a single run be READ as a picture — equity with every fill marked and
   classified — so 13-01's Task 3 can be climbed one configuration at a time instead of run as a
   seven-configuration batch whose first honest look is at the end.

This plan runs NO named-set batch and produces NO comparison table. That is 13-01 Task 3, resumed
against this plan's output.

## The defect, exactly
`13-01-IMPLEMENTATION-CONTEXT.md` section 5 measured one `ProtectivePutRule` configuration over
leading slices of the real window:

| bars | runtime | ms/bar |
|---|---|---|
| 250 | 1.50s | 5.99 |
| 500 | 5.39s | 10.78 |
| 1,000 | 17.37s | 17.37 |
| 2,000 | 57.26s | 28.63 |

ms/bar doubles as bars double. The isolating run settles the attribution: the **unhedged**
configuration, carrying no option rule at all, is flat at ~2.7 ms/bar across the same slices, while
the hedged one degrades in step with its COLUMN COUNT (96 to 168 to 312). The cost is the recorder,
not the rule and not the fill model.

The chain, with line references:
- `Book.position()` (`src/portutils/portfolio/book.py:195-202`) auto-creates a `Position` on demand
  and nothing ever removes one, so a put that expired in 2009 is still a position in 2026.
- `Book.snapshot()` (`book.py:264-268`) iterates **every** position the book has ever held.
- `StateLedger.record_book()` (`src/portutils/portfolio/ledger.py:127-139`) flattens all of them
  into one wide row as `"<SYMBOL>_<field>"`.
- `_put_row()` (`ledger.py:88-90`) widens the frame with `self.df[k] = np.nan` once per new symbol,
  copying the frame each time — the source of the `DataFrame is highly fragmented` warning every
  simulation currently emits.

A 63-bar roll over 5,201 bars is ~82 rolls, so ~82 dead legs times ~8 columns accumulate, giving
O(bars squared / 63).

## Why this is a NEW FILE and not an amendment to 13-01's boundaries
`13-01-IMPLEMENTATION-CONTEXT.md` section 6 lists four candidate fixes and concludes: *"All four
touch `Book` / `Ledger` / `PortfolioSimulator`, which 13-01's `<boundaries>` lists under DO NOT
CHANGE. None of them may be done inside this plan without an explicit amendment."*

**There is a fifth option it did not consider, and it touches none of them.**
`PortfolioSimulator.__init__` already accepts `ledger=` (`src/portutils/portfolio/simulator.py:26`,
defaulted at `:37`). So the fix is a `StateLedger` SUBCLASS in a NEW file, handed in at
construction. `Book`, `Fill`, `PortfolioSimulator`, `StateLedger` and the synthetic-marks hook are
all untouched, and no boundary amendment is required — only this plan's existence.

The byte-identity guarantee that section 6 asked for comes for free rather than by hashing: every
existing caller — `rebalance_study`, `drawdown_rotation_sim`, `overlay_runs` — passes no `ledger=`
and therefore keeps the wide `StateLedger` verbatim. Their output cannot change because their code
path does not change.

## What is given up, stated plainly so nobody rediscovers it as a bug
The narrow state frame **cannot explain its own equity path.** `"SPY 2009-03-20 P450_position"` and
its siblings cease to exist for any caller that opts in.

That is acceptable only because the per-leg story is carried by two artefacts that already exist and
are already cheap:
- `PortfolioSimulator.blotter()` (`simulator.py:128-135`) — every fill as ts, symbol, side, qty,
  price, notional. `13-01-IMPLEMENTATION-CONTEXT.md` section 7 measured this as negligible: ~164
  fills over twenty years, an O(1) dispatch per fill.
- the rule's own per-bar `state`, `drawdown`, `multiple` and `iv`, which 13-01 added to
  `synthetic_marks`.

**Therefore: any caller using `NarrowLedger` MUST persist the blotter and the rule history alongside
the equity series.** This plan states it, Task 1's module header states it, and 13-01's AC-6 and
13-02's AC-2 are amended to require all three.

  <files>src/portutils/portfolio/narrow_ledger.py, tests/test_narrow_ledger.py</files>
  <action>
    Read the objective's "The defect, exactly" and "Why this is a NEW FILE" before writing a line,
    and read `ledger.py`'s module docstring — the caller contract it specifies is what this subclass
    must preserve.

    **A NEW MODULE. Nothing existing is touched.** Do not edit `book.py`, `ledger.py`,
    `simulator.py` or the synthetic-marks hook. `PortfolioSimulator.__init__` already accepts
    `ledger=` (`simulator.py:26`, defaulted `:37`), so a subclass handed in at construction is the
    whole intervention.

    `NarrowLedger(StateLedger)` overrides `record_book` and differs in exactly two ways:

    1. **Never call `book.snapshot(prices)`.** That call is the O(dead legs) term: it iterates every
       `Position` the book has ever held, including puts that expired fifteen years ago, and builds
       a dict for each. Assemble the `TOTAL_*` fields straight off the book's own aggregates
       instead — `book.realised`, `book.unrealised(prices)`, `book.base_equity` — which is exactly
       the arithmetic `Book.snapshot` performs for its own TOTAL row (`book.py:270-279`), minus the
       per-symbol dict it then throws away. `book.unrealised` still walks every position, but that
       is a float loop over ~82 flat positions, not dict construction plus a frame widen plus a
       `.loc` assignment into an ever-wider row.

       Keep calling `book.reset_bar_counters()` after recording. `closed_units` is a within-bar
       figure and the contract that the ledger clears it immediately after writing the row is part
       of `StateLedger`'s documented behaviour, not an implementation detail.

       Record `TOTAL_closed_units` too. It is the one field a caller cannot reconstruct from the
       blotter without re-deriving which fills were closing, and it costs one sum.

    2. **Accumulate rows, materialise the frame once.** Hold `{ts: row}` rather than assigning into
       `self.df` per bar. A dict keyed by timestamp preserves the re-mark-overwrite semantic
       `_put_row` documents — a bar marked twice overwrites rather than appending a second row —
       and preserves insertion order, so the frame comes out in bar order by construction.

       Expose `df` as a property that builds `pd.DataFrame.from_dict(..., orient="index")` on first
       access and CACHES it. The caching is not an optimisation, it is a correctness requirement:
       `PortfolioSimulator.run()` reads `self.ledger.df` once after the loop and then writes
       `equity_peak`, `drawdown` and `turnover_cum` onto it (`simulator.py:116-127`), so the
       property must return the SAME mutable object on every subsequent access or those columns
       vanish. Invalidate the cache in `record_book` and in `reset()`.

       Set `df.index.name` to `self.index_name`, as `_empty()` does, so downstream code that reads
       the index by name is unaffected.

    Because the row width is fixed forever, `_put_row`'s `self.df[k] = np.nan` widening never fires
    and the `DataFrame is highly fragmented` PerformanceWarning goes with it.

    Leave `record()` — the single-asset kts.py path — entirely alone. It is not on any hot path this
    plan cares about and narrowing it would change kts.py's frame shape.

    **Comments.** The repo root `CLAUDE.md` requires the `orders/kts.py` style: a header block, then
    a short rationale comment above each meaningful step, explaining WHY. The header block must
    state, in terms: what this ledger records and what it deliberately does NOT; the measurement
    that motivated it (the ms/bar table, with its source); that **this ledger cannot explain its own
    equity path, so any caller using it must persist `sim.blotter()` and the rule's per-bar history
    alongside the equity series**; and that it is a subclass precisely so that `StateLedger`'s
    existing callers are untouched.

    Tests (`tests/test_narrow_ledger.py`), all on short windows so the suite stays fast:
    - IDENTITY — the same configuration run under both ledgers over the same 250-bar slice gives
      equity equal to 1e-12, equal final realised / unrealised, and an identical blotter.
    - CONSTANT WIDTH — column count under `NarrowLedger` identical at 250 / 500 / 1,000 bars, while
      under `StateLedger` it grows. **Assert the growth too**: the defect is shown, not asserted,
      and a test that only checks the fix would still pass if the defect silently disappeared for
      some other reason.
    - RE-MARK — recording the same timestamp twice yields one row, the second overwriting the first.
    - DF IDENTITY — `df` returns the same object on repeated access, and a column a caller writes
      onto it survives a subsequent read. This is the `simulator.run()` post-loop contract and it is
      the single easiest thing to break with a lazily-built property.
    - RESET — `reset()` empties the frame and invalidates the cache.
    - CLOSED UNITS — a bar with a closure reports it, and the next bar reports zero.

    Timing is measured in the verify step, not asserted in a test: a wall-clock assertion in CI is a
    flaky test, but an unmeasured claim is the exact failure 13-01's context section 9 calls out.
