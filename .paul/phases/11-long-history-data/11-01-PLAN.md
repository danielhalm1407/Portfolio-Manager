<objective>
## Goal

A reproducible long-history price and volatility cache spanning multiple market regimes, assembled
from IBKR where it reaches and a free source where it does not, with the provenance of every series
recorded and every gap named.

## Goal, stated as a number

The 2008 drawdown, the 2020 crash and the 2022 rate shock must all be present in the cached panel for
at least the index leg. If they are not, this plan has not succeeded, regardless of how much code was
written.

## Purpose

v0.4 claims that hedge structures improved risk-adjusted returns across many historical points and
regimes, and that parameters fitted on a backward window kept working on the forward window that
followed. Every cached panel today is **250 rows spanning 2025-07-28 to 2026-07-24** — one year, one
regime. On that data the claim is not weakly supported; it is untestable. Phases 12 to 15 are all
blocked behind this one.

This also settles a question Phase 12 cannot proceed without: whether a genuine option-implied
volatility surface is obtainable at all, or whether the option overlay must synthesise prices from
realised or VIX-implied vol. That answer must come from evidence, not assumption — consistent with
the standing project decision that on IB questions the running TWS outranks every written source.

## Output

A `portutils.ingestion.history` module, an extended `cache_prices.py`, long-history parquets under
`data/processed/`, a `COVERAGE.md` naming every gap and source, and tests that run offline.
</objective>

## AC-1: History reaches past the per-request ceiling
```gherkin
Given a symbol and a requested span longer than one IBKR request will serve
When the long-history fetcher runs
Then it issues multiple paginated requests, stitches them into one continuous series,
     and the result contains no duplicated and no silently dropped bars
And the stitch seams are verified by comparing overlapping bars between adjacent requests
```

## AC-2: Free sources fill what IBKR will not serve
```gherkin
Given a symbol whose IBKR history stops short of the requested start date
When the fetcher exhausts the IBKR path
Then it falls back to the free source for the unreachable span
And every row records which source produced it, so no series silently mixes provenance
```

## AC-3: Coverage is stated, not assumed
```gherkin
Given a completed long-history build
When the coverage report is generated
Then it names, per symbol: first and last bar, row count, source or sources, and every internal gap
And it states explicitly whether the 2008, 2020 and 2022 episodes are covered
```


  <name>Task 1: Probe the real limits before building anything</name>
  <files>src/portutils/ingestion/history.py</files>
  <action>
    Do NOT design the pagination before the ceiling is known. Phase 4 spent two plans on an
    executions limit taken from documentation that turned out to be wrong; the standing project
    decision is to probe against the live system first.

    Write a probe that records, as evidence:
    - how far back TWS actually serves '1 day' bars for a liquid index ETF (SPY), by requesting
      progressively longer durations until it refuses or returns short;
    - the exact error text or truncation behaviour when the limit is hit;
    - whether pacing violations appear, and at what request rate;
    - what the free source (yfinance, already a declared but unused dependency) returns for the same
      symbol and span, including its earliest available bar;
    - for volatility: whether an implied surface is reachable at all, a VIX-style index level, or
      neither.

    Write the findings to the plan's SUMMARY input as raw observations. Where TWS is unavailable,
    record that and run the free-source half only — a partial probe with its limits stated is a
    valid result; a guessed limit is not.

    Avoid: designing pagination windows from IB's published table without confirming them.
  </action>
  <verify>Probe output records an actual earliest-bar date per source, plus the verbatim error or truncation behaviour at the ceiling</verify>
  <done>AC-5 satisfied; the evidence AC-1's design depends on exists</done>
</task>

<task type="checkpoint:decision" gate="blocking">
  <decision>Which source is authoritative for which span, given what the probe actually found</decision>
  <context>
    The probe may show IBKR reaching 2005, or 2015, or refusing beyond a year. It may show no
    implied-vol path at all. Each outcome implies a different split between IBKR and the free
    source, and a different pricing approach for Phase 12 — and the choice determines what every
    v0.4 result can subsequently claim. This is a provenance decision about evidence the whole
    milestone rests on, so it is not one to make silently.
  </context>
  <options>
    <option id="ibkr-primary">
      <name>IBKR primary, free source only for the unreachable tail</name>
      <pros>Single broker-consistent series wherever possible; matches the live account's own data; adjustments and splits handled by one provider for most of the span</pros>
      <cons>A provenance seam sits mid-series at the handover point; two providers may disagree on adjusted closes across it, and that discrepancy must be measured and reported</cons>
    </option>
    <option id="free-primary">
      <name>Free source primary for the whole long history, IBKR only for recent bars</name>
      <pros>One consistent adjustment methodology across the entire span, so no mid-series seam; typically reaches much further back</pros>
      <cons>Free-source adjusted closes may not reconcile with the live IBKR book, weakening the link between the study and the account it is meant to inform</cons>
    </option>
    <option id="both-parallel">
      <name>Cache both in parallel and reconcile</name>
      <pros>The discrepancy between providers becomes measurable rather than assumed; strongest provenance story for a conviction write-up</pros>
      <cons>Roughly double the ingestion work and storage, and it defers rather than makes the choice</cons>
    </option>
  </options>
  <resume-signal>Select: ibkr-primary, free-primary, or both-parallel</resume-signal>
</task>
