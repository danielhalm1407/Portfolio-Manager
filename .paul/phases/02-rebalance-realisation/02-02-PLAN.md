<objective>
## Goal

Every fill the offline simulator books carries a machine-readable reason, recorded at the moment the
rule proposes the trade, and exportable as JSON in the `orders/dummy_orders.json` shape the app
already writes.

## Purpose

`research/rebalance_realisation.py` produces excellent accounting and says nothing about *why* any
trade happened. The gap is structural, not an oversight:

- `PortfolioSimulator.run()` calls `self.backend.execute(...)` with **no `ctx`**
  (`simulator.py:81`), so every `Fill`'s context fields are `None`.
- `PortfolioSimulator.__init__` builds `SimExecutionBackend(...)` with **`on_order=None`**
  (`simulator.py:38`), so no `Order` is ever built and `Order.to_dict()` is never reached offline.
- The ledger `extra` carries only portfolio-level context — `equity`, `gross_exposure`, `n_trades`,
  `turnover_notional`, `turnover_frac` (`simulator.py:90-99`). No reasoning at all.

The reasoning-rich half of the ledger is therefore exercised **only** by `orders/kts.py`, which wires
`on_order=self._register_sim_order` (`kts.py:566`) and exports `replay_orders.json` (`kts.py:3019`).
The `Order` dataclass and its `to_dict()` (`fills.py:62-125`) already exist and are complete; the
offline path simply never connected to them. This plan connects them.

This matters to PROJECT.md's core value directly: a target weight that becomes a real position is
only defensible if the book can say what justified each trade. Today it cannot, offline.

## Output

Rationale capture in all four rules, a Mapping-tolerant `ctx`, a GUI-free `build_sim_order`, a
simulator that keeps an order ledger and exports it, and a test module pinning the behaviour.
</objective>

<acceptance_criteria>

## AC-1: A rebalance trade states its own reason
```gherkin
Given a ConstantMixRule whose leg has drifted above its target weight
When the rule proposes the corrective sell
Then the rule records that leg's actual weight, target weight, weight gap, price, average entry,
     and whether the sale crystallises a gain or a loss
And it records the leg's bar return relative to the book's, so "rose more" is distinguishable
     from "fell less"
```

## AC-2: A rotation trade carries its trigger
```gherkin
Given a DrawdownRotationRule that fires on a drawdown breach
When it proposes the sleeve cut and the growth buys
Then each proposed symbol carries the event name, the drawdown that triggered it, the peak and
     trough it was measured against, and the rotation count
```

## AC-3: The reason reaches the fill and survives to JSON
```gherkin
Given a completed PortfolioSimulator run
When export_orders_json is called
Then the file parses as JSON, is keyed by string order id, and each record carries the same
     metadata / state / history nesting as orders/dummy_orders.json
And each record's metadata.rationale is non-empty for every rule-driven fill
```

## AC-4: Accounting is unchanged
```gherkin
Given the existing book, parity and migration test suites
When they run against the modified engine
Then every one passes with no numeric change
```

  <action>
    Add `self.last_rationale = {}` to `RebalanceRule`, cleared in `reset()` and at the top of every
    `propose()`. Do NOT change `propose()`'s signature or return type — it stays
    `{symbol: units}`. The rationale is a same-bar side channel the simulator reads immediately
    after each call. Changing the return type would touch kts.py and both parity suites for no
    accounting benefit.

    ConstantMixRule.propose: `actual_w = (current * px) / equity` is already computed but only
    inside the `tolerance > 0` branch (rules.py:212-216) — hoist it so it is always available, and
    record per traded symbol: rule, action (BUY/SELL), actual_weight, target_weight, weight_gap,
    delta_units, delta_notional, price, avg_entry (from `book.position(sym).avg_entry`),
    crystallises ("gain"/"loss"/"none" — only meaningful on a reducing trade), equity, bar_return,
    portfolio_bar_return, relative_return. Add `self._prev_prices`, set at the end of propose, to
    make the return fields computable; clear it in reset().

    relative_return is the field that answers the real question: a leg can be SOLD while down in
    absolute terms because it fell less than the rest of the book, and that sale can book a
    realised LOSS. Do not collapse it into the sign of bar_return.

    DrawdownRotationRule.propose: it already appends (ts, event, equity, drawdown) to self.events
    (rules.py:339) — reshape the same values into last_rationale per touched symbol, adding peak,
    trough, recovered_frac, cut_frac and rotations_used. This is re-shaping, not new computation.

    BuyAndHoldRule and TradeListRule: one-line rationale ("initial deployment", "scripted trade").

    Comment-retention policy applies: every existing comment moves with its code and is updated,
    never dropped. Match the header-block-plus-rationale style already in this module.
